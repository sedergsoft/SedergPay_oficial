# PLAN_DESPLIEGUE_TIDB_GITHUBPAGES.md — Despliegue gratuito: TiDB Cloud + GitHub Pages + backend gratuito

Estado del plan: PROPUESTA (pendiente de aprobación del equipo).

Objetivo: desplegar el MVP SEDERG_PAY con:

- **Base de datos:** TiDB Cloud (Serverless/Free, MySQL-compatible) — https://tidbcloud.com
- **Frontend:** GitHub Pages (static, Vite build)
- **Backend + contenedores restantes:** plan gratuito a seleccionar entre las opciones de la matriz (sección 3).

> **ADVERTENCIA CRÍTICA DE MOTOR DE BASE DE DATOS.**
> La línea base actual del proyecto es **PostgreSQL 17** (`docker-compose.yml#L67`, `PLAN_DE_ACCION.md`).
> **TiDB Cloud habla el protocolo MySQL, no PostgreSQL.** Este plan incluye la fase obligatoria de
> migración pg → MySQL (sección 2). Si el equipo NO acepta migrar de motor, quedarse con
> PostgreSQL y replantear la BD gratis (opción C de la sección 3).

## 2. Fase 1 — Migración del esquema pg → MySQL (obligatoria para TiDB)

### 2.1 Cambios de configuración (backend)

| Archivo | Cambio |
|---------|--------|
| `backend/config/web.php#L16` | `'dsn' => 'mysql:host=gateway01.<region>.aws.tidbcloud.com;port=4000;dbname=sederg_pay'` (vía `SEDERG_DB_DSN`) |
| `backend/config/console.php#L12` | Igual que web |
| `docker-compose.yml#L12`, `#L59` | Actualizar el valor por defecto del DSN y eliminar el servicio `postgres` del stack del despliegue cloud |
| Nuevo | Opciones PDO para TLS obligatorio en TiDB Serverless: `PDO::MYSQL_ATTR_SSL_CA` (cert `isrgrootx1.pem`) — TiDB Serverless **exige TLS**; el puerto es el **4000** del proxy, no 3306 |

Ejemplo (Yii 2, componente `db`):

```php
'db' => [
    'class'    => yii\db\Connection::class,
    'dsn'      => getenv('SEDERG_DB_DSN') ?: 'mysql:host=gateway01.<region>.aws.tidbcloud.com;port=4000;dbname=sederg_pay',
    'username' => getenv('SEDERG_DB_USER'),
    'password' => getenv('SEDERG_DB_PASSWORD'),
    'charset'  => 'utf8mb4',
    'attributes' => [
        PDO::MYSQL_ATTR_SSL_CA => '/etc/ssl/certs/isrgrootx1.pem', // TLS obligatorio
    ],
],
```

### 2.2 Cambios en migraciones

| Migración | Problema pg | Solución MySQL/TiDB |
|-----------|-------------|---------------------|
| `m261014_000001_create_sederg_pay_schema.php#L26` | `smallint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (solo Postgres) | Usar builder Yii (`$this->smallPrimaryKey()`) o `smallint AUTO_INCREMENT PRIMARY KEY` |
| `m261106_000015_add_postgresql_updated_at_triggers.php` | triggers `plpgsql` y funciones TRIGGER de Postgres | MySQL nativo: `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` en las 14 tablas de `TABLES`. Crear migración `m261108_000017` MySQL-equivalente y desactivar/retirar la pg para MySQL |
| Resto (m000002…m000016) | Mayormente builder Yii (`createTable`, `createIndex`, seeders) — portables | Auditar de todas formas: `boolean` → `tinyint(1)`, `string(190)` OK con `utf8mb4`, verificar `defaultExpression('CURRENT_TIMESTAMP')` |

### 2.3 Auditoría de SQL embebido (tarea obligatoria)

- Buscar `::` (casts Postgres), `JSONB`, `RETURNING`, `ILIKE`, `ON CONFLICT`, arrays `{}` Postgres, `NULLS LAST` en controllers/models/commands (`backend/commands`, incluida `rates/update` usada por `rate-updater`).
- Verificar transacciones/locks: `SELECT ... FOR UPDATE` es válido en MySQL; verificar niveles de aislamiento y `SERIAL` si existe.
- Probar de extremo a extremo: migrar localmente contra `mysql:8` en Docker (combo temporal `docker-compose.migration.yml`) antes de tocar TiDB Cloud.

**Criterio de salida:** `php yii migrate` corre verde contra MySQL 8 local; suite de smoke de la API OK (login, quotes, remittances).

## 3. Fase 2 — Base de datos en TiDB Cloud

1. Crear cluster **Serverless (free)** en https://tidbcloud.com → región más cercana posible (sinhay región RUS/CU; más cercana: US/SG).
2. Calidad de servicio del free tier (verificar cifras actuales en la consola, cambian con frecuencia):
   - ~5 GiB de almacenamiento de filas, cuota de Request Units (RU)/mes.
   - El cluster **pauza por inactividad** (igual que Render Free).
   - Conexión **solo por proxy TLS** en puerto 4000 → impacto directo en `docker-compose` y en `pools`/latencia (~150-250 ms RTT desde Europa/Oeste).
3. Crear **usuario de aplicación** con permisos mínimos sobre la base `sederg_pay` (no usar el usuario root generado).
4. Ejecutar migraciones: `php yii migrate --migrationPath=@app/migrations --interactive=0` desde la VM que corre el backend.
5. Seeders: re-ejecutar `m261031_000003`/`000004`/`261107_000015`.
6. Backups: TiDB Serverless no ofrece PITR completo en free; exportar dumps (`mysqldump`) con cron mensual a GitHub Private Repo o S3-compatible gratuito (Cloudflare R2 free 10 GB).

**Criterio de salida:** BD en TiDB con esquema completo y seeders; health-check del backend (`GET /health`) pasando consulta real a BD.

## 4. Fase 3 — Backend y contenedores restantes (matriz de opciones gratuitas)

El stack Docker actual del backend incluye: `backend` (php-fpm-instance yii serve), `redis`, `clamav` (clamd + freshclam, RAM pesada), `rate-updater`. Eso condiciona fuertemente las opciones "host de contenedores gratis puro".

| Opción |Qué incluye gratis | ¿Sustenta el stack completo? | Pros | Contras |
|--------|------------------|------------------------------|------|---------|
| **A. Oracle Cloud Always Free** (recomendada) | VM **Ampere A1 ARM** (hasta 4 OCPU/24 GB, 2 VMs de 1/4 OCPU), 200 GB block storage, 10 TB egress/mes — **gratuito permanente, no trial** | **Sí**: Docker Compose completo (backend, redis, clamav, rate-updater + Caddy) en una VM ARM | El único free tier "de verdad" para múltiples contenedores persistentes; no spin-down; TLS vía Caddy | Alta fricción de registro, sin región RU/CU; instancias Ampere a veces sin capacidad; requiere vigilancia dediscard billing |
| **B. Koyeb free** | 1 web service (512 MB, scale-to-zero), buildpack/docker free | **No**: no admite multi-contenedor; hay que desactivar ClamAV | Deploy en minutos, HTTPS integrado, Dockerfile del backend ya sirve | ClamAV no cabe; Redis requiere Upstash free aparte; disk efímero |
| **C. Render Free** (`render.yaml` ya existe) | 1 web service gratis, 512 MB, spin-down tras inactividad | **No** (solo servicio backend) | Ya está esbozado en repo (`render.yaml`) | Cold start hasta ~50 s; disco efímero; sin ClamAV; Redis aparte (Upstash free) |
| **D. Google Cloud Run free tier** | 2M requests/mes, scale-to-zero; container libre | Parcial (backend sí; clamav como sidecar difícil) | Imagen Docker dockerised backend directa | ClamAV no práctico; Redis→Upstash; latencia cold-start |
| **E. Fly.io** | Ya no hay free tier estable (trial/credits 2024-2026) | — | — | **Descartada para presupuesto cero sostenido** |

### Decisión recomendada

- **Primera alternativa: Opción A (Oracle Cloud Always Free VM ARM)** — es la única que mantiene el **stack completo** (incluye ClamAV, que es un requerimiento de seguridad activo I-04 en `docker-compose.yml#L48`, y Redis, necesario por el backend) **sin coste y sin apagar el servicio por inactividad**.
- Fallback si Oracle fracasa: **Opción B/D** para el backend + **Upstash Redis free** + **quitar ClamAV del despliegue cloud** (marcar `SEDERG_CLAMD_HOST` vacío y pegar feature flag) documentando el riesgo I-04 como deuda.

### Arquitectura objetivo (Opción A)

```
GitHub Pages (frontend estático, Vite)
        │  HTTPS  (API base: https://api.<dominio>.duckdns.org)
        ▼
VM Oracle ARM Ubuntu (Docker Compose)
  ├─ caddy  (TLS Let's Encrypt automático, proxy inverso)
  ├─ backend (yii serve :8080) ──► TiDB Cloud (mysql://…  gateway01, :4000, TLS)
  ├─ redis   (requirepass)
  ├─ clamav  (freshclam + clamd)
  ├─ rate-updater (loop 6 h → php yii rates/update)
  └─ volume sederg_private_data (KYC/docs privados)
```

### Sub-pasos (Opción A)

1. Alta en Oracle Cloud Free; crear VM **Ampere A1** 2 OCPU / 12 GB, Ubuntu 24.04, en región "always free eligible".
2. Seguridad: NSG solo 80/443 abiertos; SSH con clave; fail2ban.
3. Instalar Docker + Compose plugin; clonar repo privado; copiar `.env` con **secretos regenerados** (nunca commitear el `.env` actual).
4. Crear `docker-compose.production.yml` (ya existe en el repo: revisarlo y ajustar a TiDB) — eliminar servicio `postgres`, añadir `caddy` con cert autogestionado.
5. Registro DNS: dominio gratuito (DuckDNS) → A record a la IP pública de la VM.
6. `docker compose up -d` con perfil `production`; ejecutar migraciones contra TiDB; smoke test.
7. Cron de backups (`mysqldump` a Cloudflare R2/Drive) + cron `docker compose pull` opcional.
8. Alertas: presupuesto 0 USD en OCI (evitar sobrecoste accidental de A1).

**Criterio de salida:** `https://api.<dominio>/health` responde 200 consultando TiDB; frontend en Pages consume la API con CORS correcto.

## 5. Fase 4 — Frontend en GitHub Pages

El frontend es **Vite + React** (`frontend/vite.config.ts`, `frontend/package.json`, `frontend/nginx.conf` solo sirve en Docker local). GitHub Pages sirve contenido estático desde `username.github.io/<repo>/`.

1. Configurar `base` en la build:
   - Añadir a `frontend/vite.config.ts`: `base: process.env.VITE_BASE_PATH || '/'` y usar `VITE_BASE_PATH=/<repo>/` en el workflow de Pages.
   - Verificar asset paths, router `basename`, y que `index.html` no referencie rutas absolutas `/assets`.
2. Routing SPA: Pages no reescribe rutas → copiar `dist/index.html` a `dist/404.html` en el workflow (fallback de rutas deep-link).
3. API endpoint configurable: el frontend ya usa `VITE_AUTH_MODE` (build arg en `docker-compose.yml#L6`); añadir `VITE_API_URL=https://api.<dominio>` como variable de build sin `.env` en el repo.
4. GitHub Actions workflow `.github/workflows/deploy-pages.yml`:
   - triggers `push` a `main` sobre `frontend/`; `actions/setup-node` + `npm ci` + `npm run build`; Steps `actions/configure-pages`, `actions/upload-pages-artifact` (con `404.html` generado) y `actions/deploy-pages`. Empiezar con rama `gh-pages` (gh-pages desde Actions workflow sin reglas de protección si el repo mantenedor no tiene admin).
5. CORS backend: `SEDERG_CORS_ORIGINS=https://<usuario>.github.io` en `.env`/VM secretos; Accept-Origins también agregar el canon `https://<usuario>.github.io/<repo>` si Pages usa path-scope.
6. Cookies/CSRF: cookie de sesión queda en dominio del **backend** (caddie en `api.<dominio>`) — verificar `SameSite=Lax/None` según necesidad (`SEDERG_COOKIE_KEY`).
7. Enlaces míxto HTTPS obligatorio (el backend ya겠 con Caddy TLS; GitHub Pages aplica HTTPS).

**Criterio de salida:** login + quote desde `https://<usuario>.github.io/<repo>/` contra la API sin errores CORS ni CSP.

## 8. Riesgos y restricciones (transversal al plan)

| Riesgo | Impacto | Mitigación |
|--------|---------|-----------|
| TiDB free tier pausa/RU-quota | API caída cuando el cluster duerme o RU agotados | Ping cada 10 min vía cron de la VM (relativa al spin-down aceptable en sandbox); monitorear UA en consola |
| TiDB latency ~100-250 ms (sin región RU/CU) | UX quotes/ establecimientos | Métricas `health`; cachear en Redis rate-update para evitar queries en caliente |
| Sanctions/legal (EE. UU. + RU/CU data) | Riesgo regulatorio | Fase 0.4 bloqueante — decisión documentada; alternativas domésticas: Selectel/Yandex Cloud (no free but very cheap) |
| Oracle Cloud: sin capacidad A1 en region | No despliegue alternativa B/D | Fallback Opción B/D documentada |
| Multiplicación de variantes migrations pg vs MySQL | Divergencia de esquema | Mantener un único set orientado a MySQL si TiDB es el target oficial; legacy pg se archiva en branch `postgres-baseline` |
| ClamAV RAM (~1-2 GB con signatures) | Solo cabe en VM Adequate | Opción A o desactivarlo (deuda I-04) |
